2. Kickoff: dos laptops, mismo topic

Terminal tuya:

npm.cmd run chat -- --scope class --timeout 60000

Terminal del compañero (el mismo proyecto):

npm.cmd run chat -- --scope class --carnet CARNET_DEL_COMPANERO --topic cs031-s19-20261013 --timeout 60000

Al conectar cada lado envía su ping, registra recepción y acusa recibo. Si quieres escribir más mensajes usa la terminal interactiva. /quit o Ctrl+C termina. El programa imprime las dos líneas solicitadas para que tú las pegues en el chat del lab. No las envía automáticamente.

Los archivos evidence/*.jsonl registran timestamp UTC, runId, scope, public key truncada, payload y dirección remota observable del socket. remote.host: null significa que la API no expuso una dirección; no se inventa una IP. Un endpoint de loopback no prueba una IP pública, holepunch ni relay. El carnet del mensaje identifica al remitente declarado; la key autentica el transporte, no la identidad civil.

Pide al compañero su log real y cópialo a evidence/companion/. Ambos logs deben contener el mismo topicId y mensajes coincidentes por messageId. Si hay timeout, conserva el log y agrega en evidence/NOTAS.md red, versión, coordinación y pruebas autorizadas. No concluyas “UDP bloqueado” solamente porque no hubo peers. Hotspot solo si lo autoriza el instructor.

3. Archivo propio de 768 KiB

npm.cmd run sample crea samples/lab16.txt: 786432 bytes (768 KiB), texto sintético original, sin PII ni contenido de terceros. El protocolo también rechaza archivos mayores que 1,000,000 bytes, límite conservador de 1 MB.

Laptop A, seeder:

npm.cmd run seed -- --file samples/lab16.txt --scope class --timeout 300000

Copia el valor CORE_KEY mostrado en stderr o el campo key de .runtime/handoff.json. Es la clave pública del core, distinta de la key del peer y del topic del kickoff. No compartas el directorio .runtime, que contiene almacenamiento y claves de escritura.

Laptop B, downloader (reemplaza PUBLIC_KEY):

npm.cmd run download -- --key PUBLIC_KEY --scope class --delay 150 --block-timeout 15000 --timeout 120000

Usan el discoveryKey del Hypercore como topic separado para el archivo. El bloque 0 es el manifest firmado; los siguientes son fragmentos de 16 KiB. Hypercore valida su estructura autenticada y el downloader comprueba tamaño y SHA-256 del archivo reconstruido. transfer_complete y verified: true son la evidencia de integridad. El output se guarda en downloads/, sin sobrescribir archivos existentes.

La pausa está entre solicitudes secuenciales: deja tiempo para detener el seeder y evita solicitar todo el archivo de golpe. block_downloaded mide datos recibidos; progress mide datos consumidos. Si todo llegó antes del kill, terminar después no prueba que sobrevivió la red.

4. Kill-seeder manual entre compañeros

  • Empieza con un downloader nuevo (el programa crea storage único). Mantén solo el seeder A y el downloader B en ese discoveryKey.
  • En B espera a progress cerca de 50%. En A detén ese proceso Node a la fuerza. En Windows: Stop-Process -Id PID_DEL_SEEDER -Force; en Unix: kill -9 PID_DEL_SEEDER. Obtén el PID de la terminal que iniciaste; no mates todos los procesos Node.
  • Anota hora UTC del kill, PID, último bloque recibido y bytes pendientes. Guarda consola/log del seeder aunque no tenga cierre limpio. B debería registrar desconexión y timeout si nadie tiene los bloques faltantes; documenta lo que realmente ocurra.
  • Contrasta con una tercera laptop C: primero descarga todo con --stay --delay 0; espera replica_ready. Luego inicia B de cero y mata A a mitad. C permanece sirviendo el core aunque no tiene private key para escribir. Comprueba transfer_complete y qué IP/peer sirvió los bloques después del kill.
  • El número de conexiones no equivale al número de seeders completos. Un leecher solo ofrece bloques que tiene. Una DHT no aloja mágicamente tu archivo.

No se ha ejecutado una transferencia con un compañero desde este entorno. No presentes los resultados esperados como observados.

2. Discovery → transporte → datos

Texto compartido: cs031-s19-20261013
                │ SHA-256, 32 bytes
                ▼
         topic de Hyperswarm

El topic identifica un interés común, no un host ni un secreto. Para archivos se usa core.discoveryKey, topic diferente al de chat; la public key del core se comparte por coordinación humana. Esa key permite verificar el registro; no autoriza escribir. La Noise public key identifica una conexión, mientras el carnet dentro del ping es una declaración de identidad.

Como intuición de discovery, Kademlia organiza IDs con distancia XOR y contactos en k-buckets. Un lookup consulta nodos próximos a la key y refina sus candidatos. Esto distribuye el descubrimiento; no asegura privacidad, disponibilidad del contenido ni resistencia absoluta a Sybil o eclipse. Bootstrap y contactos siguen siendo necesarios. Paper original de Kademlia.

El código no implementa Kademlia desde cero: delega a HyperDHT. Hyperswarm anuncia y busca el topic en modo server+client. Cuando se emite connection, captura el endpoint expuesto por socket/rawStream. No registra “holepunch exitoso” ni “directo” basándose únicamente en esa conexión. API de Hyperswarm.

3. Infraestructura que permanece

En ejecución pública, HyperDHT configura por defecto node1.hyperdht.org:49737, node2.hyperdht.org:49737 y node3.hyperdht.org:49737, según su documentación. Son puntos de entrada, no un provider que guarda este archivo. Configurarlos no demuestra que los tres respondieron; los logs distinguen configuración de observación. Se necesitan red UDP, DNS o direcciones conocidas, routers/NAT, runtime, energía, disco y peers disponibles. HyperDHT: bootstrap e infraestructura.

El experimento local automático usa un bootstrap y un nodo persistente propios en loopback; sus puertos quedan registrados. No configura relays. En Internet puede intervenir infraestructura adicional de conectividad; si la API no permite saberlo, el informe dice no determinado. No se inventa el operador de un relay ni se concluye que no hubo ninguno.

“Zero-infra” describe retirar el servidor de aplicación que media los bits; el costo se reparte. La privacidad también cambia: el cifrado protege payloads en tránsito, pero el otro extremo puede observar su endpoint y los tiempos. Ambos conocen el topic que compartieron. No se supone que cada peer pueda listar todas las IP del swarm ni que el topic derive identidad. P2P no promete anonimato.

4. Archivo y pérdida del seeder

El generador produce texto sintético propio: 786432 bytes, sin personas ni obra ajena. Se mantiene debajo de 1 MB. El core contiene un manifest y bloques de 16 KiB. La replicación autentica los bloques y el downloader compara el SHA-256 del archivo reconstruido. El procedimiento y el estado están en KILL-SEEDER.md; los logs se enlazan desde index.html.

El controlador solicita bloques secuenciales con pausas y mata el seeder cerca de 50%. Registra por separado bytes consumidos y recibidos: una barra al 50% no prueba que queden bytes en red. Si se recibió todo antes del kill, el experimento no demuestra continuidad de disponibilidad. El contraste agrega un peer que descargó todo y queda sirviendo. Predicción comprobable: sin fuente de bloques pendientes habrá espera o fallo; con replica accesible podría completar. Estas predicciones se reemplazan por resultados observados únicamente al ejecutar. Hypercore: replicación y datos autenticados.

5. Arquitectura y liability

La comparación es una hipótesis de diseño para el lab. En un host centralizado existe un operador reconocible que puede recibir takedowns, suspender cuentas, reunir registros y responder solicitudes; el uploader también responde por su conducta. En P2P la disponibilidad y la retirada se reparten entre usuarios que conservan copias. Pedir a un seeder que deje de ofrecer contenido no borra las replicas de otros. El desarrollador todavía decide UX, distribución, publicidad y algunas dependencias.

Napster centralizaba el índice aunque el archivo pasara entre usuarios. Ese índice concentraba intervención y exposición de la compañía. BitTorrent distribuye piezas entre peers: BEP 3 usa tracker para discovery y BEP 5 añade DHT. El tracker coordina y no necesita alojar el archivo; apagar uno puede no eliminar otras rutas de descubrimiento. Ninguna de esas topologías decide por sí misma si el uso concreto es lícito. Napster: resumen del Copyright Office, BEP 3, BEP 5.

En MGM v. Grokster (2005), promover el uso infractor mediante expresiones o acciones afirmativas puede generar responsabilidad por infracciones de terceros. Descentralizar el transporte no borra esa exposición del distribuidor. Para PactTrail, la interfaz debe explicar usos autorizados de comprobantes, sin promover evasión o distribución infractora. La topología cambia puntos de control, no concede inmunidad al cliente ni al maintainer. Ficha de Oyez; opinión judicial reproducida en Justia.

6. PactTrail y Decreto 15-2026

PactTrail puede usar P2P para entregar un comprobante propio de tarea al contratante. El contrato inteligente y el procedimiento de aceptación siguen siendo otra capa: un hash acredita integridad del archivo, no que el trabajo se hizo ni que se deba pagar. Aquí no se implementaron wallets, oráculos ni pagos. Los documentos reales de trabajo pueden contener PII; por eso el lab solo transmite material sintético.

Si PactTrail encuadra como Persona Obligada o PSAV bajo Decreto 15-2026, quitar el servidor no elimina los deberes aplicables de debida diligencia/KYC, registro y reportes ante IVE/SIB. El encuadre depende de sus servicios reales, incluida posible custodia, transferencia u operación para terceros, y requiere revisar norma y reglamentación. No se atribuye automáticamente el deber empresarial al usuario que seedea un documento.

El Congreso identifica el Decreto 15-2026 y su entrada en vigor el 17 de septiembre de 2026. El paquete del curso señala un reglamento pendiente y cita art. 127; no se confirmó aquí el articulado completo ni el estado del reglamento a la fecha de ejecución, por lo que no se afirma un número de artículo o una ausencia vigente. La Iniciativa 6538 no se usa como norma promulgada. Ficha oficial del decreto, información oficial sobre PSAV y reglamentación, junio de 2026.

Aprendizaje: discovery no equivale a storage; una key no demuestra una persona; una conexión no demuestra entrega; terminar desde caché no demuestra otro seeder. El límite empírico de este trabajo se conserva junto con la evidencia, porque un fallo real vale más que una conexión inventada.

Memo zero-infra · costo, liability y revenue

PactTrail · memo de feature zero-infra

Carnet 20230285. Propuesta de producto; no se ha desplegado ni conectado un contrato inteligente en este lab.

PactTrail usa contratos inteligentes para pagar al terminar determinadas tareas. Propongo mover a P2P la entrega de comprobantes de trabajo propios entre quien ejecuta la tarea y quien la acepta. El comprobante puede ser una salida sintética, un entregable autorizado o un resumen firmado. El pago y las reglas de aceptación conservan una capa independiente. Descargar un archivo cuyo hash coincide demuestra integridad de los bits, pero no demuestra que la tarea cumple el acuerdo. La aprobación humana, un árbitro o un mecanismo de verificación explícito siguen siendo necesarios.

La experiencia sería: las partes acuerdan un identificador de entrega, descubren una fuente y obtienen el comprobante; la interfaz compara el digest esperado y presenta el resultado para aceptación. Luego el contrato aplica sus condiciones de pago. El prototipo del lab implementa discovery, intercambio y replicación. No incorpora escrow, wallets, oráculos, firmas de aceptación o liberación automática de fondos. El ejemplo transmitido contiene texto original sin personas ni contratos reales; antes de adoptar la feature habría que decidir qué documentos pueden circular, por cuánto tiempo y con qué permiso. Esa decisión debe contrastarse con STORAGE.md de S18, todavía no aportado.

El costo que podría removerse es el almacenamiento temporal y parte de la salida de datos de S3/VPS/Firebase usados para descargar esos comprobantes. Como presupuesto de volumen, no como tarifa de AWS, supongo diez mil entregas mensuales de 500 kB y dos descargas por entrega: diez GB mensuales de transferencia de documentos. Mantener una copia de todas las entregas del mes requeriría cinco GB antes de replicas. El ahorro en moneda debe calcularse con la factura real y la tarifa vigente del proveedor; no atribuyo un precio inventado. Tampoco desaparecen los gastos de blockchain, gas, indexación, soporte o desarrollo. El usuario aporta disco, red, energía y tiempo online; discovery y conectividad conservan dependencias.

La hipótesis de liability es una distribución parcial. El proveedor central deja de recibir y servir cada comprobante, y cada seeder conserva control operativo sobre su copia. Pero PactTrail sigue diseñando la interfaz, manteniendo el cliente y presentando el servicio. Su publicidad y el comportamiento que promueve importan: el precedente estadounidense Grokster sobre inducement impide tratar descentralización como inmunidad del distribuidor. El usuario tampoco adquiere permiso para compartir obras de terceros. A diferencia de un bucket central, una orden de retiro no elimina automáticamente las replicas. Habrá que establecer responsabilidades de entrega, retención y resolución de disputas antes de prometer un SLA. Grokster.

En revenue, cobraría por la coordinación del acuerdo y la gestión de hitos, sin suponer que la facturación depende de hospedar cada byte. El pago por uso podría conservarse mientras se mantenga una función de valor verificable. El ahorro de hosting puede mejorar margen, pero una descarga fallida puede aumentar soporte y reducir confianza. El acceso entre peers y la portabilidad ayudan a evitar dependencia de un único proveedor; no constituyen por sí solos un moat ni una promesa absoluta de resistencia a censura. Un seeder único offline sigue siendo una dependencia real.

Los peers pueden observar endpoints IP/puerto, tiempos e interés en el topic compartido; cifrar el transporte no vuelve anónima a la contraparte. La metadata y los comprobantes sensibles necesitan una decisión explícita antes de usar documentos reales.

Si PactTrail es Persona Obligada/PSAV bajo Decreto 15-2026, retirar el servidor no elimina debida diligencia/KYC, registro ni reportes aplicables ante IVE/SIB. El encuadre se evalúa por los servicios que efectivamente presta, especialmente si controla activos u operaciones por cuenta de terceros. La ficha oficial fija vigencia el 17 de septiembre de 2026; el articulado y estado actual del reglamento deben comprobarse antes de concretar cumplimiento. Decreto: Congreso, PSAV y reglamentación.

Dialogue journal (borrador con el límite observado)

Mi primera dependencia observable en este trabajo fue el acceso al registro de paquetes: npm devolvió EACCES al intentar instalar Hypercore. Eso impidió ejecutar Hyperswarm y el experimento de matar al seeder desde este entorno. No lo interpreto como fracaso de holepunch en el aula, porque no llegamos a esa fase. El código plantea una pregunta concreta: cuando desaparece el peer que tiene los bloques restantes, ¿quién mantiene disponible la entrega? Espero contrastar un solo seeder con una replica completa. En PactTrail esta disponibilidad puede afectar la aceptación de una tarea y, por tanto, el momento de pago.
